# Speicher210 Functional Test Bundle

A Symfony bundle with base test cases and helpers for functional testing, focused on REST endpoints.

- Snapshot assertions against expected files, with [coduo/php-matcher](https://github.com/coduo/php-matcher) patterns.
- An optional PHPUnit extension that updates the expected files from the actual output.
- Doctrine fixtures loaded per test, declared with attributes.
- Access to and mocking of container services, including private ones.
- Base test cases for console commands, forms, validators, Doctrine types, DQL functions and Twig templates.

## Requirements

- PHP 8.4 or 8.5
- Symfony 6.4, 7.4 or 8.x
- PHPUnit 12.5.8+ or 13
- Doctrine ORM 2.20+ or 3, DBAL 3 or 4

## Installation

```bash
composer require --dev speicher210/functional-test-bundle
```

Enable the bundle in `config/bundles.php`:

```php
return [
    // ...
    Speicher210\FunctionalTestBundle\Speicher210FunctionalTestBundle::class => ['dev' => true, 'test' => true],
];
```

### Configuration

The only option is the class that fixture loaders generated by the [stub command](#creating-test-stubs) extend:

```yaml
# config/packages/speicher210_functional_test.yaml
speicher210_functional_test:
    fixture_loader_extend_class: App\Tests\Fixtures\Loader\AbstractLoader # default: Speicher210\FunctionalTestBundle\Test\Loader\AbstractLoader
```

## PHPUnit setup

The bundle's bootstrap file boots the kernel once and recreates the database schema for the default entity manager.
Include it from your own bootstrap file:

```php
<?php
// tests/bootstrap.php

declare(strict_types=1);

use Symfony\Component\Dotenv\Dotenv;

require dirname(__DIR__) . '/vendor/autoload.php';

(new Dotenv())->bootEnv(dirname(__DIR__) . '/.env');

require dirname(__DIR__) . '/vendor/speicher210/functional-test-bundle/src/Test/bootstrap.php';

// Only needed when using WebTestCase::getRequestUploadLargeFile() (requires mikey179/vfsstream).
Speicher210\FunctionalTestBundle\VfsStreamSetup::initialize();
```

The schema is created only once per run, so each test has to clean up its data.
The simplest way is to run every test in a transaction with [dama/doctrine-test-bundle](https://github.com/dmaicher/doctrine-test-bundle):

```xml
<!-- phpunit.xml.dist -->
<phpunit bootstrap="tests/bootstrap.php">
    <php>
        <server name="KERNEL_CLASS" value="App\Kernel"/>
    </php>
    <extensions>
        <bootstrap class="DAMA\DoctrineTestBundle\PHPUnit\PHPUnitExtension"/>
    </extensions>
</phpunit>
```

## Test cases

| Class | Use it for |
|---|---|
| `Test\KernelTestCase` | Anything that needs the kernel: services, Doctrine, fixtures, expected files. All other test cases below build on it. |
| `Test\WebTestCase` | Requests through the `KernelBrowser`, response assertions, upload helpers. |
| `Test\RestControllerWebTestCase` | REST endpoints with JSON snapshots and authentication. |
| `Test\Command\CommandTestCase` | Console commands, with the output compared to an expected file. |
| `Test\Symfony\Form\FormTypeTestCase` | Form types: submitted data, or errors compared to an expected file. |
| `Test\Symfony\Validator\ValidatorTestCase` | Constraint validators, with common tests built in. |
| `Test\Doctrine\DBAL\Types\TypeTestCase` | Custom Doctrine DBAL types, driven by data providers. |
| `Test\Doctrine\ORM\Query\AST\FunctionTestCase` | Custom DQL functions, with an in-memory SQLite entity manager. |
| `Test\Twig\TemplateTestCase` | Twig templates, with the rendered HTML compared to an expected file. |
| `Test\Twig\IntegrationTestCase` | Twig's own integration tests, without the legacy tests. |

All classes are in the `Speicher210\FunctionalTestBundle` namespace.

## Testing REST endpoints

```php
<?php

declare(strict_types=1);

namespace App\Tests\Controller;

use App\Tests\Fixtures\Loader\LoadOneUser;
use Speicher210\FunctionalTestBundle\Attribute\WithFixture;
use Speicher210\FunctionalTestBundle\Test\RestControllerWebTestCase;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;

#[WithFixture(LoadOneUser::class)]
final class UserControllerTest extends RestControllerWebTestCase
{
    public function testReturns404IfUserIsNotFound(): void
    {
        $this->assertRestRequestReturns404('/api/users/999', Request::METHOD_GET);
    }

    public function testReturnsUser(): void
    {
        $this->assertRestGetPath('/api/users/1');
    }

    public function testUpdatesUser(): void
    {
        self::loginAsAdmin();

        $this->assertRestPatchPath('/api/users/1', ['firstName' => 'Jane']);
        $this->assertRestGetPath('/api/users/1');
    }
}
```

- **Shortcuts:** `assertRestGetPath()`, `assertRestPostPath()`, `assertRestPatchPath()`, `assertRestPutPath()` and `assertRestDeletePath()` build a JSON request and call `assertRestRequest()`. You can also call `assertRestRequest()` directly with your own `Request`.
- **Default status codes:** GET and POST expect `200`; PATCH, PUT and DELETE expect `204`. Pass another code as argument when needed.
- **Response body:** it is compared with the next [expected file](#expected-files-snapshots). For `204` responses, and when no expected file exists, the body must be empty.
- **Content type:** when an expected file exists, the response must have `application/json`, or `application/problem+json` for status codes of 400 and up. Override `getExpectedDefaultResponseContentType()` and `getExpectedErrorResponseContentType()` to change this.
- **Authentication:** `loginAs($user)` authenticates all following requests of the test as the given user; `loginAsAdmin()` uses an in-memory user with `ROLE_ADMIN`.
- **Errors:** `assertRestRequestReturns401IfUserIsNotAuthenticated()`, `assertRestRequestReturns403()` and `assertRestRequestReturns404()` compare with the bundled problem responses. Override `getExpected401Response()`, `getExpected403Response()` or `getExpected404Response()` if your API returns different ones.

`WebTestCase` adds `assertResponseStatusCode()`, `assertResponseHeaderSame()`, `assertResponseRedirectsToUrl()`, `assertResponseContentMatchesFile()` and `prepareSession()` for tests that don't use the REST helpers.

## Expected files (snapshots)

Expected files are looked up in an `Expected` directory next to the test class.
Their names are made of the test method name, the data set name when a data provider is used, and a counter that increases with every assertion in the same test:

```
tests/Controller/UserControllerTest.php
tests/Controller/Expected/testUpdatesUser-1.json
tests/Controller/Expected/testUpdatesUser-2.json
tests/Controller/Expected/testWithDataProvider-some data set-1.json
```

The expected content can use any [coduo/php-matcher](https://github.com/coduo/php-matcher) pattern:

```json
{
  "id": 1,
  "firstName": "Jane",
  "email": "@string@",
  "createdAt": "@string@.isDateTime()"
}
```

Assertions that use expected files:

| Assertion | Extension |
|---|---|
| `RestControllerWebTestCase` REST assertions | `.json` |
| `KernelTestCase::assertArrayMatchesExpectedJson()` | `.json` |
| `CommandTestCase::assertCommand()` | `.txt` |
| `FormTypeTestCase::assertFormSubmitOn*WithInvalidData()` (form errors) | `.txt` |
| `TemplateTestCase::assertTwigTemplateEqualsHtmlFile()` | `.html` |

### Updating expected files

When the `RestRequestFailTestExpectedOutputFileUpdater` extension is registered, a failing snapshot assertion rewrites its expected file with the actual output. The test still fails, so run it again to see it pass, and review the changes in the diff.
Matcher patterns such as `@string@`, `@integer@` or `@uuid@` are kept as long as they still match the actual value.

The easiest way is to register the extension only for a single run:

```bash
vendor/bin/phpunit --extension "Speicher210\FunctionalTestBundle\Extension\RestRequestFailTestExpectedOutputFileUpdater"
```

To add a new REST snapshot, create the expected file with `{}` as content (the [stub command](#creating-test-stubs) can do this) and run the test with the extension.
`assertArrayMatchesExpectedJson()` creates missing expected files itself while the extension is registered.

#### Fixed values and matcher patterns

The extension always uses the default matcher patterns (`Json::DEFAULT_MATCHER_PATTERNS`) and no fixed values.
To change them, enable the updater yourself in the bootstrap file instead of registering the extension:

```php
// tests/bootstrap.php
use Speicher210\FunctionalTestBundle\SnapshotUpdater\Driver\Json;
use Speicher210\FunctionalTestBundle\SnapshotUpdater\DriverConfigurator;

if (getenv('UPDATE_SNAPSHOTS') === '1') {
    DriverConfigurator::createDrivers(
        fields: ['createdAt' => '@string@.isDateTime()'],
        matcherPatterns: Json::DEFAULT_MATCHER_PATTERNS,
    );
    DriverConfigurator::enableOutputUpdater();
}
```

```bash
UPDATE_SNAPSHOTS=1 vendor/bin/phpunit
```

- `fields` are JSON keys whose values are always written with the given value, at any depth. This is useful for values that change on every run, like timestamps.
- `matcherPatterns` are the patterns that are kept in the expected file as long as they still match.

Don't register the extension at the same time: when the run starts, it resets the drivers to its defaults.

#### Updating expected files from your own assertions

`SnapshotUpdater` can update the expected file of any assertion that fails with a comparison failure.
Catch the `ExpectationFailedException`, update the file when the updater is enabled, and rethrow the exception:

```php
use PHPUnit\Framework\ExpectationFailedException;
use Speicher210\FunctionalTestBundle\SnapshotUpdater;
use Speicher210\FunctionalTestBundle\SnapshotUpdater\DriverConfigurator;

protected function assertCsvExportMatchesExpected(string $actualCsv): void
{
    // Next expected file of the test: Expected/<test>-<n>.csv
    $expectedFile = $this->getExpectedContentFile('csv');

    try {
        self::assertStringEqualsFile($expectedFile, $actualCsv);
    } catch (ExpectationFailedException $e) {
        $comparisonFailure = $e->getComparisonFailure();
        if ($comparisonFailure !== null && DriverConfigurator::isOutputUpdaterEnabled()) {
            SnapshotUpdater::updateText($comparisonFailure, $expectedFile);
        }

        throw $e;
    }
}
```

The expected file has to exist (it can be empty), otherwise the assertion fails without a comparison failure.
Pick the method that matches the actual value in the comparison failure:

| Method | Actual value in the comparison failure | Written as |
|---|---|---|
| `SnapshotUpdater::updateJson()` | Decoded JSON, as from the `JsonContentMatches` constraint | JSON indented with 2 spaces, keeping matcher patterns and applying fixed values |
| `SnapshotUpdater::updateText()` | String, as from `assertStringEqualsFile()` | As is |
| `SnapshotUpdater::updateXML()` | `DOMDocument`, as from `assertXmlStringEqualsXmlFile()` | Formatted XML |
| `SnapshotUpdater::updateBinary()` | Binary string, as from the `ImageSimilarity` constraint | As is |

## Fixtures

Fixtures are Doctrine fixtures. Extend `Test\Loader\AbstractLoader` and yield the entities to persist:

```php
<?php

declare(strict_types=1);

namespace App\Tests\Fixtures\Loader;

use App\Entity\User;
use Generator;
use Override;
use Speicher210\FunctionalTestBundle\Test\Loader\AbstractLoader;

final class LoadOneUser extends AbstractLoader
{
    #[Override]
    protected function doLoad(): Generator
    {
        yield new User(1, 'John', 'Doe');
    }
}
```

The loaders to run before each test are declared with attributes:

- `#[WithFixture(Loader::class)]` on the test class loads the fixture for every test of the class. It is repeatable.
- `#[WithFixture(Loader::class)]` on a test method loads it for that test only.
- `#[WithFixture(Loader::class)]` on a trait loads it for every test of the classes that use the trait, including through parent classes.
- `#[WithFixtureForTest(Loader::class, 'testName')]` on the test class loads it only for the given test. This is meant for tests inherited from a parent class.

You can also override `getAlwaysLoadingFixtures()`, or put a PHP file that returns a list of loader classes in a `Fixtures` directory next to the test class, named after the test (`Fixtures/testReturnsUser.php`).

Loaders that need services can implement `Test\Loader\LoaderAsService`. They are then fetched from the container by their class name instead of being instantiated.
Register them as public services in the test environment, otherwise Symfony removes them from the container as unused.

## Request payload files

Large request payloads can be kept in files in a `Fixtures/data` directory next to the test class, named like expected files (`Fixtures/data/testCreatesUser-1.php`).
`getPayloadFromPhpFile()` returns the array from the next PHP payload file of the test, and `getPayloadContentFile('json')` returns the path of the next payload file of another type.
When a data provider is used, a file without the data set name is used if no file with it exists.

## Services and Doctrine

- `getContainerService(Foo::class)` or `getContainerService(Foo::class, 'service_id')` returns a service from the test container, including private services.
- `mockContainerService('service_id', $mock)` replaces a service. To replace services before the fixtures are loaded, return them from `servicesToMock()` instead.
- `getEntityManager()`, `getObjectManager()` and `clearObjectManager()` give access to Doctrine.
- `getEntity()`, `findEntity()` and `findAllEntities()` are shortcuts to read entities.
- `getDefaultDatabaseConnection()` and `restartDatabaseSequences()` work with the database connection.

## Uploaded files

`Test\DummyFile` is an enum of bundled sample files: images (BMP, GIF, JPG, PNG, SVG, an SVG with an XSS payload, WebP), MP3 with and without tags, MPEG video, PDF, text and XLSX.
Each case provides `path()`, `content()`, `base64Content()`, `mimeType()`, `splFileInfo()` and `uploadedFile()`.

`WebTestCase` also has `getRequestUploadImageFile()`, `getRequestUploadPdfFile()`, `getRequestUploadTextFile()`, `getRequestUploadAudioFile()`, `getRequestUploadVideoFile()` and `getRequestUploadLargeFile()`.
Images of a custom size need `ext-imagick`, and large files need `mikey179/vfsstream` plus `VfsStreamSetup::initialize()` in the bootstrap file.

## Other test cases

### Console commands

```php
final class ImportUsersCommandTest extends CommandTestCase
{
    public function testImportsUsers(): void
    {
        $this->assertCommand('app:users:import', ['file' => 'users.csv']);
    }
}
```

The exit code must be `0` (pass another expected code as the fourth argument), and the output is compared with `Expected/testImportsUsers-1.txt`.

### Form types

Implement `formTypeUnderTest()` and submit data with `assertFormSubmitOnPost()`, `assertFormSubmitOnPatch()` or `assertFormSubmitOnGet()`, which compare the form data with the expected data.
The `*WithInvalidData()` variants assert that the form is invalid, and compare its errors with an expected file.
Register the types, extensions and type extensions your form needs by overriding `getTypes()`, `getExtensions()` and `getTypeExtensions()`.
Form types that depend on the `RequestStack` can get `$this->requestStackMock`; its current request is a mock with the submitted method, data and files.

### Doctrine DBAL types

Implement `classUnderTest()`, `getTypeName()` and the four data providers for valid and invalid values in both directions. The conversion tests are built in.

### DQL functions

Return your functions from `registeredStringFunctions()` and use `getEntityManager()`, backed by an in-memory SQLite database with the stub entities from `Test\Doctrine\ORM\Query\AST\Fixtures`.

### Validators

`ValidatorTestCase` extends Symfony's `ConstraintValidatorTestCase`. Implement `createValidator()`, `createConstraint()` and `createValidValue()`; tests for invalid values, invalid constraints and `null` are built in.

### Twig templates

`assertTwigTemplateEqualsHtmlFile($template, $context)` renders a template and compares it with `Expected/<test>-<n>.html`. `mockTwigFunction()` replaces a Twig function for the current test.

## Traits and helpers

| Helper | Description |
|---|---|
| `Test\Carbon\CarbonClockSensitiveTestCase` | Freezes Carbon's clock during each test (at `2022-09-13 17:48:56.123`, or call `freezeClock()`). |
| `Test\Symfony\Clock\SymfonyClockSensitiveTestCase` | Freezes the Symfony clock during each test, at `2022-09-13 17:48:56.123`. |
| `Test\Assert\Pdf` | Compares a PDF's text or page images with expected files. Needs `spatie/pdf-to-text`, `spatie/pdf-to-image` and `ext-imagick`. Supports the updater extension. |
| `Test\Assert\Image` | `assertImageSimilarity()` compares two images. Needs `ext-imagick`. Included in `KernelTestCase`. |
| `Test\MockObject\AbstractClass` | `createMockForAbstractClass()` mocks the abstract methods of a class and keeps its concrete methods. |
| `Test\PHPUnitHelper` | `withConsecutive()` replaces PHPUnit's removed method of the same name. Included in `KernelTestCase`. |
| `Comparator\MoneyPHP` | PHPUnit comparator for `moneyphp/money`. Register it in the bootstrap file with `SebastianBergmann\Comparator\Factory::getInstance()->register(new MoneyPHP());`. |

`KernelTestCase` also includes coduo's `PHPMatcherAssertions` (`assertMatchesPattern()`), and restores the default `Locale` after each test.

### "No expectations were configured" notices

PHPUnit 12.5 and later report a notice for mock objects without expectations.
`TypeTestCase` and `FormTypeTestCase` create such mocks (`$platform`, `$currentRequestMock` and `$requestStackMock`) for every test.
PHPUnit only reads the opt-out attribute from the test class itself or the test method, not from parent classes, so add it to your test classes.
The built-in `TypeTestCase` tests already have it.

```php
use PHPUnit\Framework\Attributes\AllowMockObjectsWithoutExpectations;

#[AllowMockObjectsWithoutExpectations]
final class MyFormTypeTest extends FormTypeTestCase
{
}
```

## Creating test stubs

The bundle provides a command that creates the files of a new test:

```bash
bin/console sp210:test:stub:create tests/Controller testCreatesUser --expected=2 --payloads=1
```

The directory must already contain a `*Test.php` class, which is used to find the namespace. The command creates:

- `Expected/testCreatesUser-1.json` and `-2.json`, with `{}` as content.
- `Fixtures/data/testCreatesUser-1.php`, a payload file.
- `Fixtures/Loaders/TestCreatesUser.php`, a fixture loader extending the configured `fixture_loader_extend_class`. Skip it with `--no-loader`.

It then prints the `#[WithFixture]` attribute to add to the test.
