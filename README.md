# Speicher210 Functional Test Bundle

A Symfony bundle with base test cases and helpers for functional testing, focused on REST endpoints.

- Snapshot assertions against expected files, with [coduo/php-matcher](https://github.com/coduo/php-matcher) patterns.
- A PHPUnit extension that updates the expected files from the actual output.
- Doctrine fixtures loaded per test, declared with attributes.
- Access to and mocking of container services, including private ones.
- Base test cases for console commands, forms, validators, Doctrine types, DQL functions and Twig templates.
- End-to-end tests in a real browser with Playwright, with the same fixtures, mocks and expected files.

## Requirements

- PHP 8.4, 8.5 or 8.6
- Symfony 6.4, 7.4 or 8.1+
- PHPUnit 12.5.8+ or 13
- Doctrine ORM 2.20+ or 3, DBAL 3 or 4

## Installation

```bash
composer require --dev speicher210/functional-test-bundle
```

Enable the bundle in `config/bundles.php`:

```php
return [
    // ...
    Speicher210\FunctionalTestBundle\Speicher210FunctionalTestBundle::class => ['dev' => true, 'test' => true],
];
```

The only configuration option is the base class of the fixture loaders generated by the [stub command](#creating-test-stubs):

```yaml
# config/packages/speicher210_functional_test.yaml
speicher210_functional_test:
    fixture_loader_extend_class: App\Tests\Fixtures\Loader\AbstractLoader # default: Speicher210\FunctionalTestBundle\Test\Loader\AbstractLoader
```

## PHPUnit setup

The bundle's bootstrap file boots the kernel once and recreates the database schema for the default entity manager.
Include it from your own bootstrap file:

```php
<?php
// tests/bootstrap.php

declare(strict_types=1);

use Symfony\Component\Dotenv\Dotenv;

require dirname(__DIR__) . '/vendor/autoload.php';

(new Dotenv())->bootEnv(dirname(__DIR__) . '/.env');

require dirname(__DIR__) . '/vendor/speicher210/functional-test-bundle/src/Test/bootstrap.php';
```

If you need more than the schema from the Doctrine metadata, see [Preparing the test environment](#preparing-the-test-environment).

Then register the PHPUnit extensions:

```xml
<!-- phpunit.xml.dist -->
<phpunit bootstrap="tests/bootstrap.php">
    <php>
        <server name="KERNEL_CLASS" value="App\Kernel"/>
    </php>
    <extensions>
        <!-- Runs every test in a database transaction that is rolled back afterwards. -->
        <bootstrap class="DAMA\DoctrineTestBundle\PHPUnit\PHPUnitExtension"/>

        <!-- Uncomment to update the expected files of failing snapshot assertions. -->
        <!--
        <bootstrap class="Speicher210\FunctionalTestBundle\Extension\SnapshotUpdaterExtension">
            <parameter name="fields" value='{"createdAt": "@string@.isDateTime()"}'/>
        </bootstrap>
        -->
    </extensions>
</phpunit>
```

- **Database:** the schema is created only once per run, so each test has to clean up its data. [dama/doctrine-test-bundle](https://github.com/dmaicher/doctrine-test-bundle) does this by running every test in a transaction.
- **Snapshots:** the `SnapshotUpdaterExtension` writes the actual output into the expected files. It's only meant to be enabled while you update them, see [Updating expected files](#updating-expected-files).

### Preparing the test environment

`TestEnvironment::prepare()` boots the test kernel, runs the given steps in order and shuts the kernel down.
The bundle's bootstrap file is the short form of `TestEnvironment::prepare(new RecreateSchemaFromDoctrineMetadata())`.
Call `prepare()` yourself instead of including that file, for example to create database views:

```php
// tests/bootstrap.php
use Speicher210\FunctionalTestBundle\Test\Bootstrap\ExecuteSqlFiles;
use Speicher210\FunctionalTestBundle\Test\Bootstrap\RecreateSchemaFromDoctrineMetadata;
use Speicher210\FunctionalTestBundle\Test\Bootstrap\TestEnvironment;

TestEnvironment::prepare(
    new ExecuteSqlFiles([__DIR__ . '/views/customer_report/drop.sql']),
    new RecreateSchemaFromDoctrineMetadata(),
    new ExecuteSqlFiles([__DIR__ . '/views/customer_report/create.sql']),
);
```

Or to use the migrations:

```php
use Speicher210\FunctionalTestBundle\Test\Bootstrap\RunCommand;
use Speicher210\FunctionalTestBundle\Test\Bootstrap\TestEnvironment;

TestEnvironment::prepare(
    new RunCommand('doctrine:migrations:migrate'),
);
```

| Step | Description |
|---|---|
| `RecreateSchemaFromDoctrineMetadata` | Drops the schema and creates it again from the Doctrine metadata, for the default or a named entity manager. |
| `ExecuteSqlFiles` | Executes SQL files in the given order, on the default or a named connection. |
| `RunCommand` | Runs a console command. Its output is only shown when it fails. Needs `symfony/console`. |
| Any callable | Gets the booted kernel: `static fn (KernelInterface $kernel) => …`. |

- **Failing steps:** an exception or a command that fails stops the test run.
- **Views:** `RecreateSchemaFromDoctrineMetadata` doesn't drop views, and PostgreSQL doesn't drop tables that a view uses. Drop the views first, in reverse order if one uses another.
- **SQL files:** put a single statement in each file. Not all database drivers accept several, or report the errors of all of them.
- **Commands:** arguments and options are passed as an array, like `['--allow-no-migration' => true]`. Options that change the verbosity, like `-v`, have no effect.
- **Separate processes:** PHPUnit includes the bootstrap file again for a test that runs in a separate process (`#[RunInSeparateProcess]`), so the steps run again.
  The test before it can still hold locks on the database, and recreating the schema then waits for them forever. Run such tests with their own PHPUnit configuration and a bootstrap file without these steps.

### Running tests in parallel

Each worker of [ParaTest](https://github.com/paratestphp/paratest) includes the bootstrap file too, so it needs its own database:

```yaml
# config/packages/doctrine.yaml
when@test:
    parameters:
        env(TEST_TOKEN): '1'
    doctrine:
        dbal:
            dbname_suffix: '_%env(TEST_TOKEN)%'
```

ParaTest sets `TEST_TOKEN` to the number of the worker: with a database `app_test`, the workers use `app_test_1`, `app_test_2` and so on.

- **Without ParaTest:** the default token is used, so PHPUnit uses the database of worker 1. Don't run both at the same time.
- **Creating the databases:** they have to exist. If the database user may create databases, start with `new RunCommand('doctrine:database:create', ['--if-not-exists' => true])`.
- **Other connections:** only Doctrine's connections get the suffix. What reads `DATABASE_URL` directly, like Symfony's `PdoSessionHandler`, still uses the database without it, so that one has to exist too.

## Expected files (snapshots)

Most assertions of the bundle compare the actual output with an expected file in an `Expected` directory next to the test class.
The file name is made of the test method name, the data set name when a data provider is used, and a counter that increases with every assertion in the same test:

```
tests/Controller/UserControllerTest.php
tests/Controller/Expected/testUpdatesUser-1.json
tests/Controller/Expected/testUpdatesUser-2.json
tests/Controller/Expected/testWithDataProvider-some data set-1.json
```

Expected files can use any [coduo/php-matcher](https://github.com/coduo/php-matcher) pattern for values that aren't known in advance:

```json
{
  "id": 1,
  "firstName": "Jane",
  "email": "@string@",
  "createdAt": "@string@.isDateTime()"
}
```

REST responses and arrays are compared as JSON, console output and form errors as text, Twig templates as HTML, and PDFs by text and page images.
REST responses and console output without an expected file must be empty, so tests of commands that print nothing don't need one.

### Updating expected files

Expected files don't have to be written by hand.
While the `SnapshotUpdaterExtension` is registered, every failing snapshot assertion rewrites its expected file with the actual output.
The test still fails that one time; run it again to see it pass, and review the changes in the diff before committing them.

Enable it only when updating snapshots: uncomment it in `phpunit.xml.dist` (see [PHPUnit setup](#phpunit-setup)), or register it for a single run:

```bash
vendor/bin/phpunit --extension "Speicher210\FunctionalTestBundle\Extension\SnapshotUpdaterExtension"
```

When updating JSON files, the extension keeps what makes snapshots stable:

- **Matcher patterns** in the expected file, such as `@string@`, `@integer@` or `@uuid@`, are kept as long as they still match the actual value.
  The `matcherPatterns` parameter replaces the list of patterns to keep, as a JSON list (default: `Json::DEFAULT_MATCHER_PATTERNS`).
- **Fixed values** from the `fields` parameter, a JSON object, are always written for those keys, at any depth.
  Use it for values that change on every run, like timestamps.

To add a new REST snapshot, create the expected file with `{}` as content (the [stub command](#creating-test-stubs) can do this) and run the test with the extension.

The extension was previously called `RestRequestFailTestExpectedOutputFileUpdater`. The old name still works, but it is deprecated.

### Updating expected files from your own assertions

Your own snapshot assertions can use the same mechanism: catch the `ExpectationFailedException`, update the file when the updater is enabled, and rethrow the exception.

```php
use PHPUnit\Framework\ExpectationFailedException;
use Speicher210\FunctionalTestBundle\SnapshotUpdater;
use Speicher210\FunctionalTestBundle\SnapshotUpdater\DriverConfigurator;

protected function assertCsvExportMatchesExpected(string $actualCsv): void
{
    // Next expected file of the test: Expected/<test>-<n>.csv
    $expectedFile = $this->getExpectedContentFile('csv');

    try {
        self::assertStringEqualsFile($expectedFile, $actualCsv);
    } catch (ExpectationFailedException $e) {
        $comparisonFailure = $e->getComparisonFailure();
        if ($comparisonFailure !== null && DriverConfigurator::isOutputUpdaterEnabled()) {
            SnapshotUpdater::updateText($comparisonFailure, $expectedFile);
        }

        throw $e;
    }
}
```

`SnapshotUpdater` has a method for each kind of content the assertion compares: JSON, text, XML or binary.
The expected file has to exist, even empty, because an assertion on a missing file fails without a comparison failure.

## Test cases

| Class | Use it for |
|---|---|
| `Test\KernelTestCase` | Anything that needs the kernel: services, Doctrine, fixtures, expected files. All other test cases below build on it. |
| `Test\WebTestCase` | Requests through the `KernelBrowser`, response assertions, upload helpers. |
| `Test\RestControllerWebTestCase` | REST endpoints with JSON snapshots and authentication. |
| `Test\Command\CommandTestCase` | Console commands, with the output compared to an expected file. |
| `Test\Symfony\Form\FormTypeTestCase` | Form types: submitted data, or errors compared to an expected file. |
| `Test\Symfony\Validator\ValidatorTestCase` | Constraint validators, with common tests built in. |
| `Test\Doctrine\DBAL\Types\TypeTestCase` | Custom Doctrine DBAL types, driven by data providers. |
| `Test\Doctrine\ORM\Query\AST\FunctionTestCase` | Custom DQL functions, with an in-memory SQLite entity manager. |
| `Test\Twig\TemplateTestCase` | Twig templates, with the rendered HTML compared to an expected file. |
| `Test\Twig\IntegrationTestCase` | Twig's own integration tests, without the legacy tests. |
| `Test\Playwright\E2ETestCase` | End-to-end tests in a real browser, see [End-to-end tests with Playwright](#end-to-end-tests-with-playwright). |

All classes are in the `Speicher210\FunctionalTestBundle` namespace.

## Testing REST endpoints

```php
<?php

declare(strict_types=1);

namespace App\Tests\Controller;

use App\Tests\Fixtures\Loader\LoadOneUser;
use Speicher210\FunctionalTestBundle\Attribute\WithFixture;
use Speicher210\FunctionalTestBundle\Test\RestControllerWebTestCase;
use Symfony\Component\HttpFoundation\Request;

#[WithFixture(LoadOneUser::class)]
final class UserControllerTest extends RestControllerWebTestCase
{
    public function testReturns404IfUserIsNotFound(): void
    {
        $this->assertRestRequestReturns404('/api/users/999', Request::METHOD_GET);
    }

    public function testReturnsUser(): void
    {
        $this->assertRestGetPath('/api/users/1');
    }

    public function testUpdatesUser(): void
    {
        self::loginAsAdmin();

        $this->assertRestPatchPath('/api/users/1', ['firstName' => 'Jane']);
        $this->assertRestGetPath('/api/users/1');
    }
}
```

- Each REST assertion sends a JSON request, checks the status code, and compares the response body with the next expected file. When there is no expected file, or for `204 No Content`, the body must be empty.
- Responses compared with an expected file must be `application/json`, or `application/problem+json` for errors. Both can be changed by overriding a method.
- `loginAs()` and `loginAsAdmin()` authenticate the requests that follow in the test.
- The 401, 403 and 404 assertions compare with bundled problem responses, which can be replaced as well.

## End-to-end tests with Playwright

`Test\Playwright\E2ETestCase` runs tests in a real browser with [playwright-php/playwright-symfony](https://github.com/playwright-php/playwright-symfony).
It extends that package's `PlaywrightTestCase` and adds the fixtures, service mocks and expected files of `KernelTestCase`, through the `Test\Concern\FunctionalTest` trait.

Install the package and a browser. The installer needs Node.js 20 or later:

```bash
composer require --dev playwright-php/playwright-symfony:^0.12
vendor/bin/playwright-install chromium
```

Enable its bundle for the test environment in `config/bundles.php`:

```php
return [
    // ...
    Playwright\Symfony\PlaywrightSymfonyBundle::class => ['test' => true],
];
```

```php
<?php

declare(strict_types=1);

namespace App\Tests\E2E;

use App\Tests\Fixtures\Loader\LoadOneUser;
use Speicher210\FunctionalTestBundle\Attribute\WithFixture;
use Speicher210\FunctionalTestBundle\Test\Playwright\E2ETestCase;

#[WithFixture(LoadOneUser::class)]
final class UserProfileTest extends E2ETestCase
{
    public function testShowsUser(): void
    {
        $this->visit('/users/1');
        $this->assertPageContains('John Doe');

        $response = $this->getLastResponse();
        self::assertNotNull($response);
        static::assertResponseContentMatchesFile($response, $this->getExpectedResponseContentFile('html'));
    }
}
```

- The browser's requests are handled by the kernel of the test, in the same PHP process. Fixtures, mocked services and the DAMA transaction apply to them, also across several `visit()` calls.
- Fixtures are declared like in the other test cases. Playwright's own `loadFixtures(array)` hook is final and throws an exception.
- For the page and the response, use Playwright's assertions and helpers. The `KernelBrowser` helpers and response assertions of `WebTestCase` are not available, except `assertResponseContentMatchesFile()` and `assertJsonResponseContent()`, which take the response from `getLastResponse()`.
- `PlaywrightTestCase` removes all exception handlers in `tearDown()`, also the ones that were active before the test. PHPUnit then reports the test as risky ("removed exception handlers other than its own").
  This happens when a kernel is booted outside a test, like in the bundle's bootstrap file, and `symfony/runtime` is not installed: Symfony's `ErrorHandler` then stays registered as exception handler. Install `symfony/runtime`, which Symfony Flex applications already have, to avoid it.

### JavaScript errors

`assertPageHasNoErrors()` fails the test if the page threw an uncaught JavaScript error or logged a `console.error()`.
It checks everything since the page was opened, not only since the last navigation, and the failure lists every recorded error.
Console warnings and other messages are ignored. It needs `playwright-php/playwright` 1.6 or later.

```php
public function testCheckout(): void
{
    $this->visit('/cart');
    $this->click('button[type=submit]');
    $this->assertPageContains('Thank you for your order');

    self::assertPageHasNoErrors();
}
```

Without an argument, it checks the current page of the test. Pass a page to check another one, for example a popup: `self::assertPageHasNoErrors($popup)`.

### Live Components and Turbo

A [Live Component](https://symfony.com/bundles/ux-live-component/current/index.html) re-renders through a request after a field changes.
If the test acts during that request, its action can be lost: for example, the morph undoes a value it typed, or a click on "Save" is swallowed.
`waitUntilNothingIsBusy()` waits until no element is marked with `aria-busy="true"`, which Live Components and Turbo set while they load:

```php
public function testUpdatesTheTotal(): void
{
    $page = $this->visit('/cart');

    $page->locator('#cart_quantity')->fill('3');
    $page->locator('#cart_quantity')->press('Tab');
    self::waitUntilNothingIsBusy();

    $this->click('button[type=submit]');
    $this->assertPageContains('Total: 30.00');
}
```

- **Blur:** a model bound with `on(change)`, like a form with `data-model="on(change)|*"`, only updates when the field loses focus, so press `Tab` first.
- **Debounce:** a Live Component starts its request only after a debounce, so nothing is busy right after the event. The wait therefore lasts at least 200 ms. That is longer than the default 150 ms debounce of models updated on input. For a model with a longer `debounce()`, pass a longer quiet period: `self::waitUntilNothingIsBusy(quietPeriod: 600)`.
- **Timeout:** it fails with Playwright's timeout if something stays busy, including markup that keeps `aria-busy="true"` permanently. Without an argument, it waits on the current page of the test.

## Fixtures

Fixtures are Doctrine fixtures. Extend `Test\Loader\AbstractLoader` and yield the entities to persist:

```php
<?php

declare(strict_types=1);

namespace App\Tests\Fixtures\Loader;

use App\Entity\User;
use Generator;
use Override;
use Speicher210\FunctionalTestBundle\Test\Loader\AbstractLoader;

final class LoadOneUser extends AbstractLoader
{
    #[Override]
    protected function doLoad(): Generator
    {
        yield new User(1, 'John', 'Doe');
    }
}
```

Declare the loaders to run before each test with attributes:

- `#[WithFixture(Loader::class)]` on the test class loads the fixture for every test of the class. It is repeatable.
- `#[WithFixture(Loader::class)]` on a test method loads it for that test only.
- `#[WithFixture(Loader::class)]` on a trait loads it for every test of the classes that use the trait, including through parent classes.
- `#[WithFixtureForTest(Loader::class, 'testName')]` on the test class loads it only for the given test. This is meant for tests inherited from a parent class.

Loaders that need services can implement `Test\Loader\LoaderAsService`. They are then fetched from the container instead of being instantiated.
Register them as public services in the test environment, otherwise Symfony removes them from the container as unused.

## Other helpers

- **Container services:** `KernelTestCase` gives access to services, including private ones, and can replace them with mocks, also before the fixtures are loaded.
  Parameters are read with a Psl type that the value is coerced to, also from static methods: `self::getContainerParameter('app.host', Type\non_empty_string())`.
- **Doctrine:** shortcuts for the entity manager, for reading entities, and for resetting database sequences.
- **Request payloads:** large payloads can be kept in a `Fixtures/data` directory next to the test class, named like expected files.
- **Uploaded files:** `Test\DummyFile` is an enum of bundled sample files (images, audio, video, PDF, text, XLSX), and `WebTestCase` creates uploaded files from them. Large files need `mikey179/vfsstream`.

| Trait or class | Description |
|---|---|
| `Test\Carbon\CarbonClockSensitiveTestCase` | Freezes Carbon's clock during each test. |
| `Test\Symfony\Clock\SymfonyClockSensitiveTestCase` | Freezes the Symfony clock during each test. |
| `Test\Assert\Pdf` | Compares a PDF's text or page images with expected files. Needs `spatie/pdf-to-text`, `spatie/pdf-to-image` and `ext-imagick`. |
| `Test\Assert\Image` | Compares two images. Needs `ext-imagick`. Included in `KernelTestCase`. |
| `Test\MockObject\AbstractClass` | Mocks the abstract methods of a class and keeps its concrete methods. |
| `Test\PHPUnitHelper` | `withConsecutive()`, a replacement for PHPUnit's removed method. Included in `KernelTestCase`. |
| `Comparator\MoneyPHP` | PHPUnit comparator for `moneyphp/money`. Register it in the bootstrap file. |
| `Comparator\DoctrineCollection` | PHPUnit comparator for Doctrine collections. Needs PHPUnit 13.3+, see [Comparing Doctrine collections](#comparing-doctrine-collections). |
| `Exporter\DoctrineCollectionExporter` | PHPUnit object exporter for Doctrine collections. Needs PHPUnit 13.3+, see [Comparing Doctrine collections](#comparing-doctrine-collections). |

### Comparing Doctrine collections

A built entity holds an `ArrayCollection` and a persisted one a `PersistentCollection`.
`assertEquals()` fails on the class alone, and exporting the failure walks the entity manager, which can take forever.
With PHPUnit 13.3 or later, register the comparator and the exporter in the bootstrap file:

```php
// tests/bootstrap.php
use PHPUnit\Util\Exporter as PHPUnitExporter;
use SebastianBergmann\Comparator\Factory as ComparatorFactory;
use Speicher210\FunctionalTestBundle\Comparator\DoctrineCollection;
use Speicher210\FunctionalTestBundle\Exporter\DoctrineCollectionExporter;

ComparatorFactory::getInstance()->register(new DoctrineCollection());
// PHPUnit's own registry, not the comparator factory's exporter: only it also reaches the failure messages PHPUnit writes itself.
PHPUnitExporter::registerObjectExporter(DoctrineCollectionExporter::namingElements());
```

- **Register both:** the exporter prints every collection class the same way, so without the comparator the diff doesn't show that only the class differs.
- **Order:** collections are compared by their values in order, and keys are ignored. A compared to-many association needs an order-by in its mapping (`#[ORM\OrderBy]`), otherwise it loads in whatever order the query plan returns.

### "No expectations were configured" notices

PHPUnit 12.5 and later report a notice for mock objects without expectations.
`TypeTestCase` and `FormTypeTestCase` create such mocks for every test.
PHPUnit only reads the opt-out attribute from the test class itself or the test method, not from parent classes, so add it to your test classes.
The built-in `TypeTestCase` tests already have it.

```php
use PHPUnit\Framework\Attributes\AllowMockObjectsWithoutExpectations;

#[AllowMockObjectsWithoutExpectations]
final class MyFormTypeTest extends FormTypeTestCase
{
}
```

## Creating test stubs

The bundle provides a command that creates the files of a new test:

```bash
bin/console sp210:test:stub:create tests/Controller testCreatesUser --expected=2 --payloads=1
```

The directory must already contain a `*Test.php` class, which is used to find the namespace. The command creates:

- `Expected/testCreatesUser-1.json` and `-2.json`, with `{}` as content.
- `Fixtures/data/testCreatesUser-1.php`, a payload file.
- `Fixtures/Loaders/TestCreatesUser.php`, a fixture loader extending the configured `fixture_loader_extend_class`. Skip it with `--no-loader`.

It then prints the `#[WithFixture]` attribute to add to the test.
